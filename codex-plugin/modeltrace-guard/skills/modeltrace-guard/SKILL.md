# ModelTrace Guard Autoswitch

This is the independent `modeltrace-guard-autoswitch` plugin, marketplace `modeltrace-autoswitch`, based on xqy2006/ModelTrace with fork work by ChenCJ-io. The retained source/skill directory name is `modeltrace-guard`. It uses ordinary `codex` after one-time setup and preserves consent for **each incident**. Since 0.5 there is no configured primary: a new conversation starts on CCSwitch's current default card and stays on that card until the user switches it in the conversation. The old preauthorized recovery workflow does not apply.

Resolve `../../scripts/autoswitch.mjs` and `../../scripts/guard.mjs` relative to this skill. Ordinary monitoring needs Node.js 18+ and a compatible native Codex app-server runtime. The complete gateway workflow requires both zstd and native HTTPS `proxyEnv` support: use Node.js 24.5+ or at least 22.21 on the 22.x line; Node.js 25+ is also supported. Configuration checks need a `sqlite3` CLI with `sha3()`. Probe generation consumes inference usage; scoring uses the bundled offline bank.

## Original task and disposable sampling forks

These management instructions apply to the original task. In a runner-created fork whose new input begins `[ModelTrace Guard: disposable sampling fork]`, answer the requested integer-array task exactly once. Do not run tools, manage monitoring, continue the inherited goal or report status. This exception permits probe generation only inside the runner's sampling fork; the original task's messages and goal remain unchanged.

## Use in an ordinary Codex conversation

When the user says “使用 modeltrace-guard-autoswitch” or asks to turn on fingerprint monitoring (“开启指纹监测”, “enable fingerprint monitoring”) in a normal `codex` conversation, execute `node <autoswitch> use --session <actual-thread-id>`. Use `CODEX_THREAD_ID` or the trusted native session ID; never invent an ID or monitor another task. Do not ask the user to type a special launcher or start another CLI on their behalf. `use` enables monitoring only after this thread has a successful gateway receipt on the card it started on; a thread that already switches routes (or whose monitoring was turned off) is monitored again on its current route. It never grants switch approval.

Interpret the result truthfully. `monitoring_enabled` or `alreadyEnabled` applies only to this thread. `personal_route_unmonitored` leaves the initial or selected Official route without automatic probes. `existing_policy` means an incident or switch request is still open; settle it first, `use` never clears a halt. Explicit ordinary personal diagnostics can use `guard start`, but never start those merely to make `use` appear successful.

If gateway configuration is missing or `use` returns `connection_setup_required`, complete the one-time preparation below within the user's setup/use request. Announce its scope: it changes this Codex home's future conversation defaults, not the current running thread or monitoring of all conversations. Do not add a redundant permission question when the user already requested this setup/use; this authorization never covers a later incident switch. `connect` creates the configuration itself; there is no primary to ask for.

After `connect`, inspect `connection-status`. Only when `use` returns `new_conversation_required` (no gateway route or receipt for this thread), explain that the first old conversation cannot be hot-attached and ask the user to create a fresh ordinary Codex conversation once, then say “使用 modeltrace-guard-autoswitch” there. Finish the authorized setup before this handoff. Do not report the old thread as monitored, loop `use` to manufacture a receipt, restart the daemon, or substitute `launch --resume` as though it reroutes the original window.

`gateway_request_failed` means this thread already reached the gateway but its request failed. Read the bounded `lastRequest.statusCode`, `responseEvent` and `failureHint`; diagnose that same route instead of asking for another conversation. `gateway_request_unconfirmed` means a route was selected without a confirmed response, not an old unconnected thread. `gateway_configuration_changed` means its saved evidence belongs to another configuration. `gateway_not_ready` means the installed entry has an unavailable service or old implementation, or new conversations cannot use CCSwitch's current default card (`gateway.newConversations` says why: proxy mode off, no default card, failover on for a card only CCSwitch reaches, ...); repair that before suggesting another conversation. None enables monitoring or authorizes switching. An HTTP 403 saying “only allows Codex official clients” does not establish that the account lacks Codex access: CCSwitch Stack forwarding (used only for CCSwitch-managed logins that are not the default card) may strip native client headers, while CCSwitch's default route and direct relays keep them. Compare paths before attributing fault. Never spoof client identity to work around a rejection.

## One-time setup and configuration

When the user asks to check the setup (“检查 ModelTrace 环境”), when installation, `connect` or `use` fails, or before guiding a new user through setup, run `node <autoswitch> check`. It is read-only. Present each item in the user's language with its status (ok, todo, fail, skip) and, for todo/fail, its fix, in the listed order; `next` is the first thing to do. Do not change CCSwitch settings, sign in, or trust hooks for the user; run setup commands only within an explicit setup request. `ready: true` means the environment is complete, not consent to anything.

For installation before this skill is available, use the user-supplied repository URL or local directory and read that checkout's root `INSTALL.md`. Do not invent a published fork URL or use the upstream repository as this fork. The installation helper installs a local marketplace/plugin and optionally saves an explicitly named recommended backup; it never calls `connect`, starts monitoring, reads authentication files or changes hook trust. Installation alone does not authorize changing native defaults.

Interpret natural language directly; no keyword parser is needed. There is no primary to configure. “主渠道用 X” or “默认用 X” means the user wants new conversations to start on X: tell them to select X as the default Codex card in CC Switch (in Routing or Aggregation mode); to move the current conversation, use `switch-route`. “推荐备用用 Relay B” / “异常时优先推荐 Relay B” maps to `configure --backup-name "Relay B"`. Changing only the recommended backup keeps the configuration ID (`configurationKept: true`), works while the gateway runs and affects no open conversation. A different `--port` or `--cc-switch-dir` needs a new configuration ID: `gateway-stop`, `configure`, then `connect` (which starts the gateway and updates Codex's entry record); conversations opened before then need a new conversation, so tell the user first. The backup is optional: an incident lists every CCSwitch Codex card, and the backup only becomes the recommended entry; it cannot be a card usable only as CCSwitch's default card. Preferences are **not switch approval**. Use `inspect` to obtain actual candidates. Resolve an exact name first; only when none matches may a unique case-insensitive match be used. If the matching level is ambiguous, show its candidates and obtain the intended ID with `configure --backup-provider <ID>`; do not supply name and ID modes together or invent IDs. `configure` without a backup clears the recommendation. Optional settings are `--cc-switch-dir <path>` (default `~/.cc-switch`) and `--port <number>` (default `15722`).

New conversations start on CCSwitch's default card, which is defined only while CCSwitch runs its local proxy for Codex (Routing or Aggregation mode); in its Direct mode CCSwitch rewrites Codex's configuration on every card change and bypasses the gateway. A conversation binds to the default card on its first request and keeps that card; changing CCSwitch's default only affects newer conversations. Per card: a key-based Responses card is a direct relay, and CCSwitch only provides it. A card that cannot be reached directly (for example it needs CCSwitch's format conversion) or whose login CCSwitch manages (GitHub Copilot, xAI OAuth) uses CCSwitch's ordinary default route while it is CCSwitch's default card: before forwarding, the gateway checks that CCSwitch runs its proxy, the card is still its default card and its automatic failover is disabled; drift stops the request and never silently selects another card. A conversation on such a card therefore fails once CCSwitch's default card changes: the user selects it again in CC Switch or starts a new conversation. A CCSwitch-managed login that is not the default card must be added to CCSwitch Aggregation to be a switch target. For a direct relay, when that card is the conversation's route, the gateway reads its saved CCSwitch configuration (base_url, key, static headers) for each request, sends the request straight to that card's base_url with the card's own key, and drops the native ChatGPT login, account and other credential headers. The card's identity hash binds the route: after the card is edited or removed in CCSwitch, conversations on it are refused (a new conversation uses the edited card). Official uses the fixed official HTTPS endpoint and only supports the current CLI's native ChatGPT login with no managed account. Preserve the company default configuration. Do not edit the CCSwitch database, inspect other credential stores, change the global default or restart the whole Codex application to implement routing. Inspection SQL returns identity flags and hashes; only a direct relay route reads its own card's key, in memory, never printed or saved. The HTTP gateway receives native authentication headers and forwards them only on the local-CCSwitch or fixed-official path; do not parse or save login tokens, or claim the gateway never receives them.

Official egress is separate from route configuration. The gateway reaches the fixed Official endpoint from its own Node process, which may have been started by a hook or tool call without the user's proxy variables, and Node does not read OS proxy settings by itself. The default `auto` uses the gateway process's `HTTPS_PROXY`/`https_proxy`, then the OS system HTTPS proxy (macOS `scutil --proxy`, Windows Internet Settings), then a direct connection; it is re-resolved about every 15 seconds and after any connection failure, so a proxy that starts, stops or changes port takes effect without a restart. `network` shows the gateway process's live egress plus a credential-free reachability check. `network --official-proxy <auto|direct|http(s)://HOST:PORT>` saves an explicit choice that applies immediately, without stopping the gateway, a new configuration ID, route migration or any consent. Map “官方渠道走代理 127.0.0.1:7890” to `network --official-proxy http://127.0.0.1:7890`. Change it only at the user's request, never to make a switch succeed on your own initiative. SOCKS-only and PAC system proxies are reported as `socks_unsupported` / `pac_unsupported`; ask the user for an HTTP(S) proxy port instead. Never print proxy credentials; outputs are already redacted.

Configuration updates require a stopped gateway and generate a new configuration ID; existing routed threads are not silently migrated. `connect` creates a missing configuration and updates one from before 0.5 (`config_outdated`: a fixed primary): it keeps the capability token, port, CCSwitch directory and a still-usable recommended backup, and changes nothing until every check passes (CCSwitch proxy with a default card, native login, trusted startup hook); only then it stops the old gateway and starts the updated one. Conversations opened before need a new conversation, including the one that runs `connect`: it cannot continue afterwards. Tell the user before running it there, and offer the terminal command `node <autoswitch> connect` (also shown in the startup notice) instead. While the configuration is outdated, `gateway-start` and `configure` refuse, and `gateway-stop` stops the old gateway. It also requires a signed-in native login in the current Codex home (ChatGPT, ChatGPT tokens or an API key) and the trusted synchronous startup hook. Relay routes never forward the native credential (CCSwitch replaces it; a direct relay never receives it), so any of these logins works for them; only an OpenAI Official target needs a ChatGPT login, and approval refuses it otherwise without using the user's reply. A user without an OpenAI account can sign in with any API key (`codex login --with-api-key`). Authentication checks explicitly select `openai` for their own app-server process because CCSwitch's global provider may be `custom`; this check does not sign the user in. If it returns `account: null`, report what this process observed and verify the active home/provider; do not infer the user has never signed in. Never read or copy another profile's credentials, or treat company API-key availability, installation or offline tests as proof of native readiness.

Run `connect` for authorized one-time setup. It starts the gateway and uses compare-and-swap checks to write only `model_provider="openai"` and `openai_base_url` in the current Codex home's base user config, saving their original values. These are defaults for future new conversations. It does not modify auth, another home such as `.codex-personal`, CCSwitch's default card, the daemon or a running thread. The changed defaults route new conversations through the gateway, starting on CCSwitch's default card; monitoring remains off until that thread opts in. On `conflict`, `overridden` or stale configuration, report the actual limitation instead of bypassing ownership checks or changing unrelated defaults.

Setup and ordinary startup must discover the same data directory. `connect` rejects a command-only `--data-dir` that differs from ordinary startup's lookup; use this home's default, or ensure both setup and ordinary `codex` inherit the same `MODELTRACE_AUTOSWITCH_DATA`. Do not solve a path mismatch by silently modifying unrelated shell profiles.

CCSwitch exit, restart or a user card change can rewrite the two defaults; setup does not permanently own them. On a renewed user setup/use request, explicit `connect` may restore gateway defaults only while each current key equals its saved original or old owned value. Any other value remains a conflict. Report the actual result; never bypass these checks or perform background reconnection. This restores future defaults, not a running thread or incident approval.

The synchronous `SessionStart` handler in `startup.mjs` ensures the gateway is started only when this plugin's owned integration is ready. It never enables monitoring, rewrites native defaults or repairs CCSwitch drift automatically. When a conversation opens or resumes (not after compaction), it also shows the user one line naming the card this conversation uses (for a new conversation, CCSwitch's current default card; for a resumed one, its own card and which card new conversations now get) and whether monitoring is on, and how to turn it on. When that card cannot be used it says why the conversation's requests will fail: CCSwitch's proxy is off, no default card, automatic failover on for a card only CCSwitch reaches, CCSwitch's default card changed for a card only usable as its default card, the card was edited or removed, or Official without a ChatGPT login. A conversation that bypasses the gateway is told where it actually goes (for example CCSwitch's current card or a personal Official subscription). The user already sees this line, so do not repeat it unless asked. For a new conversation it names the route its first request will receive; actual routing evidence remains the gateway receipt, and the notice is never consent. Respect native hook trust; a newly added or changed startup hook needs the user's review in `/hooks`. `gateway-start` alone starts a service and does not connect ordinary Codex defaults.

`connection-status` reports `readyForNewThreads` and the future-default integration state. Actual routing for the current thread requires its successful gateway receipt and route state. Account identity, quota UI, a healthy gateway, config-file contents or a successful write are not current-route evidence. Keep these scopes separate in reports.

On an explicit disconnect request, run `disconnect`; it restores only the two defaults still owned by this integration, and refuses to overwrite outside changes. It does not stop existing gateway sessions, monitoring or the gateway. Use their respective commands when the user requests those actions.

`enable --session <UUID>` remains the lower-level command for an already-connected thread. `launch`, `launch --provider-name <NAME>` and `launch --resume <UUID>` remain advanced diagnostic compatibility commands, not the ordinary entry flow. They do not hot-modify the original window or guarantee portability of old authentication/encrypted history. Keep user task names; for ordinary `guard start --name`, use a verified task title, never a shared workspace name. Keep this fork separate from the upstream monitor on the same thread and from other Codex homes.

## First mismatch: report and ask

For the main gateway workflow, the **first valid fingerprint mismatch** pauses work and creates an `awaiting_approval` request. Strong difference signals and weak ranking disagreements both require a report; explain which occurred. Missing metadata, an unlisted model, invalid output, timeout, compaction, interruption or absent route evidence are coverage gaps, not valid mismatches. A sample carrying `confusableGroup` is `compatible`: its candidate differs from the expected model only inside a validated group the bank cannot separate (currently `gpt-6.1-sol` / `gpt-6-astra`). It is neither a mismatch nor a passed identity check; if asked, say the candidate is in the same known confusable group, not that the model was confirmed or substituted. It also satisfies the fingerprint condition of a target verification.

Before another work tool or a final result, report the expected model, fingerprint candidate, checkpoint time, signal strength and proposed target. Say “fingerprint candidate,” never a verified backend identity or proof of reduced reasoning effort. Do not secretly add retries, contact a backup, or run a target canary while awaiting approval. Pause edits, commands, delegation and ordinary task work while asking the user whether to switch to the proposed target, choose another target, or keep the current route. Subagents' tool calls are denied while the parent task is paused; do not delegate around the pause.

Only after visibly reporting pending notifications may you run the returned `guard acknowledge --alert <ids>` for the alerts actually described. **Acknowledgement means the agent has reported the alert; it is not user consent.** Do not acknowledge silently or equate an acknowledgement with independent delivery proof. Installation, connect, saving a recommended backup, use/enable, a previous incident's approval, silence and timeout do not approve this incident. Do not convert a broad earlier assignment into standing permission to switch.

Report and acknowledge in the same turn, then end the turn. `approve-switch`, `decline-switch` and `resume` are accepted only after a user reply that arrives after the acknowledgement: their next message, or an answer to a blocking `request_user_input`. Each reply settles at most one decision, so a failed verification needs a new reply before another approval. If a command reports that it needs the user's reply, tell the user and wait; never retry it in the same turn.

Use the current request ID from status. Run the incident commands through `node <guard>` (`guard.mjs`). After reporting and acknowledging, run `candidates --request <ID>` and show the user its numbered list in their language: each selectable entry's number, name, kind, whether monitoring stops (Official, which uses the current Codex login and its subscription) or continues after switching, and its last check if present; then the unavailable entries with their hint (for example a card not yet added to CCSwitch Aggregation); and 0 = keep the current route. Mark the recommended entry when the list has one. Listing binds each number to that exact card for this request and sends no target request. When the user answers with a listed number, run `choose --request <ID> --pick <N>`; for a card name, `choose --request <ID> --target-name <NAME>`. `choose` records consent for that one target and starts its verification in one step; a different target than the proposed one gets a new request ID, so continue with the ID it returns. A card edited after it was listed is refused: list again and ask again. If the user added a card in CCSwitch and asks to refresh, list the candidates again; that is not consent. 0, “不切换” or “继续用当前的” means `decline-switch`. `propose-switch --request <ID>` (default backup, or `--target-name`/`--target-provider`) and `approve-switch` remain available for a single proposed target; `propose-switch` creates a new pending proposal without sending target requests and is not a read-only status command. To select another target, use `--target-name <NAME>` or `--target-provider <ID>`, not both. Resolve names with `inspect` using exact-first, then unique case-insensitive matching; duplicate names require choosing an ID. If the recommended backup is already the current route or no target is proposed, ask the user to choose another actual configuration; never infer a return to the card the conversation started on. Merely proposing a target never approves it. Every proposal creates a new `switchRequest.id`: use the returned ID for approval, waiting or decline, never the superseded ID.

“同意切到 <目标名>” or “选 2” is an explicit selection and approval for the current incident: execute `choose` for that target without asking again. A bare “同意” approves only the entry marked recommended, or the single selectable entry when there is exactly one. If the target identity or configuration changes, select it again and obtain new consent; approval of an old ID/configuration cannot transfer to a different target. If the user's reply is genuinely ambiguous about switching or target, clarify while leaving the task paused.

When the user declines switching and asks to continue the current route, execute `decline-switch --request <ID>`. This keeps the route, resumes task work and restores ordinary third-party monitoring intervals; it does not disable future incident reports. Do not silently reinterpret “continue” as approval to switch.

## Approved verification and continuation

For an Official target, `approve-switch` first runs the gateway's reachability check. `OFFICIAL_UNREACHABLE` means nothing was approved, the user's reply was not consumed and the request stays `pending`. Report the reported cause (for example `ECONNRESET via a direct connection`) and ask the user to fix network access or choose a proxy; once they confirm the switch again, approve that same pending request. A failed verification diagnostic may include `gateway` (status code, `transportError`, `networkSource`) and `upstream` (Codex's final error text): use them to tell a local network failure from an account, quota or fingerprint problem.

After explicit approval, use `wait-switch --request <ID>` to observe the native canary. Never call it as a substitute for obtaining consent, and never turn elapsed waiting time into approval. The target canary needs a real `completed` receipt tied to the approved route/configuration **and** a compatible fingerprint. A queued job, HTTP success, fabricated receipt or classifier candidate alone is insufficient.

Keep original work paused until the recorded successful verification commits the target route and releases this request's halt. On failure or changed conditions, keep the halt, explain the returned diagnostic and do not call ordinary `resume` to bypass verification. Once failure cleanup has settled, list the candidates for the failed request again (each entry shows its latest check, including this failed verification) and let the user answer; `choose` on the failed request creates a fresh request with a new ID and no inherited approval, and needs the user's new reply. Do not retry or choose another target automatically. Report the successful route change before continuing the still-requested task; the user's incident-specific approval already authorizes completing that verified switch, so no repeated permission question is needed.

A successful Official switch stops probes so further automatic monitoring does not spend the personal subscription. A successful third-party switch keeps monitoring this thread; its next mismatch creates a new request and requires new consent. Never automatically return to the card the conversation started on; a return happens only through the user-requested switch below, after its own verification. Earlier approvals do not cover later anomalies or targets.

`disable --session <UUID>` stops monitoring and cancels pending probes while preserving the selected route, evidence and any halt. `gateway-stop` stops the proxy; sessions relying on it cannot send subsequent requests until it restarts. Do not confuse stopping monitoring with stopping the gateway or releasing a halt.

## User-requested route switch

When the user explicitly asks to move this thread to a configuration ("切到 API2 copy", "切回原来的渠道", "switch to Doro", "切到 OpenAI Official"), run `node <guard> switch-route --target-name <NAME>` (or `--target-provider <ID>`), then observe with the returned request ID through `wait-switch --request <ID>`. When the user asks to switch without naming a target ("换个渠道", "有哪些渠道"), run `candidates` without `--request`, show the list and switch only after the user names one. "原来的渠道"/"开始时的渠道" means the card this conversation started on (`sessionStart` in `candidates`), "默认卡" CCSwitch's current default card (`ccswitchDefault`); resolve other names with `inspect`, exact first, then a unique case-insensitive match, and ask when ambiguous. If the user wants all new conversations on a card, that is CCSwitch's default card: tell them to select it in CC Switch. The user's request is consent for that one target: do not ask again, and never run `switch-route` on your own initiative, for a target the user did not name, or to retry a failure.

It changes only this thread's gateway route; it never edits CCSwitch's default card or other threads, and Codex needs no restart. It does not require monitoring: a thread that went through the gateway but has no route policy gets a routing-only one (monitoring stays off, also after the switch), created only when every check has passed. It refuses while an incident or switch request is open (settle that with propose/approve/decline or an explicit resume), while standalone `guard start` monitoring runs without a route policy (the user stops it with `guard stop` or turns on consent monitoring with “开启指纹监测”), and when the conversation's model is absent from the fingerprint bank (`MODEL_NOT_IN_BANK`: the target could never be verified). Before routing changes, one canary probe verifies the target exactly like an incident switch: a completed route receipt plus a compatible fingerprint (a validated confusable-group match counts). This protects against switching back to a relay that still serves another model; it spends one probe on that target. Original work stays paused during verification. On `autoswitch_verified`, report the new route: a monitored thread keeps monitoring on a third-party route, a thread without monitoring stays unmonitored (offer “开启指纹监测” if relevant), a successful Official switch stops monitoring, and monitoring that only paused for Official resumes when the user switches back to a third-party route. On `report_switch_failed_current_route_kept`, the thread keeps its current route, the pause is already released and monitoring is restored to its previous state; report the reason and any fingerprint candidate (not proof of substitution) and continue the task on the current route only if still requested.

Key-based cards need no CCSwitch setup. A card whose login CCSwitch manages must be added to CCSwitch Aggregation unless it is CCSwitch's default card; if `switch-route` or `candidates` says so, tell the user to add it in the CCSwitch interface. A card that cannot be reached directly (for example it is not a Responses API provider, or reads its key from an environment variable) is reported with its reason and is not selectable. Never edit the CCSwitch database. An Official target also passes the gateway reachability check first (`OFFICIAL_UNREACHABLE` means nothing started).

## Native sampling and evidence boundaries

Normal checkpoints run in background native hooks and save normal results silently. Do not execute `probe`, poll status, wait or narrate each normal check. A foreground `probe` is only for a diagnostic explicitly requested by the user. External-terminal enable/start cannot wake an idle task; its next loaded trusted hook handles queued work.

**Never generate, type, copy or submit probe numbers in the monitored task.** Direct `submit --numbers` is unsupported. Do not substitute an ordinary fork tool, a subagent, another model or a hand-written provider request when the runner fails. Report recorded coverage gaps and diagnostic code/stage honestly; a queued follow-up is not a completed check.

The runner creates a native persisted frozen baseline without starting a model turn in it. Sampling forks are ephemeral, text-only and limited to one requested response; trusted hooks block their tools. Their model/provider and route bindings must come from the source task and verified route metadata, not the classifier's prediction. Raw arrays remain in local sample storage, not parent tool results. Native forks use saved history, not unseen in-flight memory; a mid-turn snapshot may include an interruption marker.

The baseline is cleaned up after its checkpoint or standalone retry batch. Never use or edit it if it briefly appears in the task list. Cleanup refuses original tasks, altered baselines and baselines with persisted descendants, including archived ones; report pending or blocked cleanup rather than calling archiving deletion. Do not delete unrelated tasks to fix cleanup. A turn-boundary hash is not a transcript-content hash.

Probe arrays do not become parent history. Language variation and fixed prefixes do not guarantee an invisible test or cache hit; report actual cached-token counts when available, and treat null as unavailable. A fork samples its own continuation, not proof of the backend used by an earlier parent request. Same-context and multilingual false-positive rates are not independently calibrated; correlated probes cannot justify multiplying independent error probabilities.

Async alerts arrive at the next safe Codex boundary and do not wake an idle task. Trusted synchronous `PreToolUse` blocks supported subsequent work tools, not all hosted paths or already-running commands. Never promise immediate cancellation of every action or that the plugin killed Codex. At most one checkpoint runs per task; expiry, changed comparison conditions, interruption and late results do not become mismatch votes.

## Optional standalone upstream monitoring

Use `guard.mjs start` when the user separately requests ordinary upstream monitoring. This is distinct from the gateway consent workflow: it keeps the upstream same-baseline retry batch and never grants route-switch permission. Do not start it to evade an awaiting-approval request or restart stopped personal monitoring without a new explicit diagnostic request.

Run `start` with only requested overrides:

- `--expected <exact-label>` chooses a bank label; `auto` follows native metadata. `models` lists labels. Missing metadata and an unlisted label are separate non-mismatch outcomes.
- `--tool-min 16 --tool-max 32` gives the default random interval of observed work-tool completions; equal bounds give a fixed interval. No elapsed-time schedule or turn/task count caps.
- `--retry-count 3` means 3 additional retries after the first standalone mismatch; range 1–100. “复测改成 5 次” maps to `guard configure --retry-count 5`, not to hidden retries in the consent workflow.
- `--pending-seconds 180` is the issuance-to-completion deadline, not sampling frequency.
- `--languages zh,en,ja,ko,fr,de,es,pt,ru,ar` selects the pool; defaults are zh,en and a single language fixes it.

`guard configure` preserves evidence and counters. An active standalone batch keeps its original target, language, count, model comparison, bank and frozen context. The initial mismatch is not one of N retries. After visibly notifying and acknowledging, use the returned `guard wait --confirmation <ID>` only during the anomaly; each wait observes progress, returns within 30 seconds and does not generate probes. Pause original work until all N complete, even if one matches. Every retry forks the same initial baseline and boundary, never a prior child or the extended parent; do not nest batches or capture a replacement baseline.

In standalone mode, matching retries advance automatically and mismatching retries require notification and acknowledgement. All N valid mismatches preserve `taskHalt` and deny supported subsequent work tools. Stop original work and wait for an explicit user resumption request. Only then read the current halt ID and run `guard resume --halt <ID>`. Acknowledgement, configuration, model changes and stop/start do not clear it. Do not use standalone `resume` in place of the gateway approve/decline workflow.

## Readiness, trust, dashboard and storage

`guard doctor` verifies bundled files. `doctor --fork true` additionally creates native snapshot/ephemeral forks without inference, checks runtime settings and trusted sync/async hooks, then queues cleanup. Read readiness and deletion status honestly. `MODELTRACE_CODEX_PATH` can select the intended executable; never fix readiness by changing an unrelated account/provider or bypassing trust.

Respect an already completed hook review. If the runtime reports untrusted hooks or changed definitions, ask the user to review ModelTrace Guard Autoswitch in Codex CLI's `/hooks`; do not run trust-changing commands yourself. Reload the plugin when required. Untrusted fork protection refuses inference rather than falling back to an unsafe path.

`status` reports current requests, saved route and monitoring state alongside gateway/connection readiness; use actual receipts before claiming which channel handled a request. Stopped monitoring does not mean a stopped gateway. The synchronous startup readiness check and background monitoring hooks have separate purposes: only already-enabled monitoring schedules probes. Do not reactivate stopped Official monitoring implicitly. Verification requires newly observed work-tool/background-hook activity in the current runtime, not just an old timestamp. Long idle time means waiting for work activity, not proven health or failure.

After an authorized plugin upgrade, `gateway-status` must show the installed `implementationVersion`. `upgrade_required` means the old owned daemon is still running, even if it answers health checks. Stop and start only this plugin's gateway during the repair/upgrade, keeping the existing configuration, capability and routes; do not restart the Codex application or reset approval state. Startup reports this condition rather than silently interrupting existing gateway requests. Starting the transport does not require CCSwitch's default card to be usable, so conversations on their own cards recover after a restart; `gateway-status.newConversations` reports whether new conversations can start, and each request on CCSwitch's default route still checks the default card and failover settings.

When asked for a dashboard, run `guard dashboard` and open the returned local URL. Keep its capability fragment and the gateway capability URL private; do not publish them or remove authentication/Origin checks. Browser notifications need permission and a connected page, and an existing alert is not proof of delivery. The page does not export probe arrays, transcripts or credentials. `dashboard-stop` stops only the web service; hook monitoring does not depend on it. `guard stop` cancels standalone sampling and preserves any halt/history.

The default data directory is `${CODEX_HOME:-~/.codex}/modeltrace-guard-autoswitch`, isolated from the upstream monitor. See `../../README.md` for storage, cleanup and calibration details. The packaged bank is a snapshot; do not collect or expand it without a separate user request. Synthetic tests and scorer parity do not establish independent long-context or multilingual accuracy. Standalone web search/images endpoints are unsupported; encrypted history can be nonportable, so never promise full endpoint compatibility or lossless cross-route continuation.
